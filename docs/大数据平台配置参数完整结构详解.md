# 大数据平台配置参数完整结构详解

## 1. service_ddl.json 文件顶级结构

```json
{
  "name": "HDFS",                         // 服务唯一标识符
  "label": "HDFS",                        // 服务显示名称
  "description": "分布式大数据存储",        // 服务描述
  "version": "3.3.3",                     // 服务版本号
  "sortNum": 1,                           // 服务在列表中的排序顺序
  "dependencies": [                       // 服务依赖列表
    "ZOOKEEPER"
  ],
  "packageName": "hadoop-3.3.3.tar.gz",   // 安装包文件名
  "decompressPackageName": "hadoop-3.3.3",// 解压后的目录名
  "roles": [],                            // 服务角色定义(详见第2节)
  "configWriter": {},                     // 配置文件生成器定义(详见第3节)
  "parameters": []                        // 配置参数定义(详见第4节)
}
```

## 2. roles 服务角色结构

```json
"roles": [
  {
    "name": "NameNode",                   // 角色唯一标识符
    "label": "NameNode",                  // 角色显示名称
    "roleType": "master",                 // 角色类型: master/worker/client
    "runAs": {                            // 运行身份
      "user": "hdfs",                     // 运行用户
      "group": "hadoop"                   // 运行用户组
    },
    "cardinality": "1+",                  // 角色基数(如最少数量)
    "sortNum": 2,                         // 角色在列表中的排序顺序
    "logFile": "logs/hadoop-hdfs-namenode-${hostname}.log", // 日志文件路径
    "jmxPort": "27001",                   // JMX监控端口
    "startRunner": {                      // 启动脚本定义
      "timeout": "60",                    // 超时时间(秒)
      "program": "control_hadoop.sh",     // 执行程序
      "args": [                           // 程序参数
        "start",
        "namenode"
      ]
    },
    "stopRunner": {                       // 停止脚本定义
      "timeout": "600",
      "program": "control_hadoop.sh",
      "args": [
        "stop",
        "namenode"
      ]
    },
    "statusRunner": {                     // 状态检查脚本定义
      "timeout": "60",
      "program": "control_hadoop.sh",
      "args": [
        "status",
        "namenode"
      ]
    },
    "restartRunner": {                    // 重启脚本定义
      "timeout": "60",
      "program": "control_hadoop.sh",
      "args": [
        "restart",
        "namenode"
      ]
    },
    "externalLink": {                     // 外部访问链接
      "name": "NameNode Ui",
      "label": "NameNode Ui",
      "url": "http://${hostname}:9870"
    }
  }
]
```

## 6. 配置参数分组机制详解

配置参数分组机制是大数据平台配置管理的核心特性，它通过三个关键字段（configCategory、configGroup和configLevel）来实现对参数的分类组织，使配置更加结构化和易于管理。

### 6.1 配置分组核心字段

| 字段名 | 类型 | 可选值 | 说明 |
|-------|------|------|------|
| `configCategory` | 字符串 | "role"/"kubernetes" | 参数分类，角色配置需设置为"role"，Kubernetes配置需设置为"kubernetes"，通用配置文件配置不需要设置此字段 |
| `configGroup` | 字符串 | 角色名或配置文件名 | 角色配置需设置为对应的角色名，通用配置文件配置不需要设置此字段 |
| `configLevel` | 字符串 | "basic"/"advanced"/"custom" | 参数级别，角色配置需设置此字段，自定义配置需设置为"custom"，通用配置文件配置不需要设置此字段 |

### 6.2 配置分组工作原理

1. **角色与配置文件分离**：
   - `configCategory = "role"`：参数与特定角色（如NameNode、ResourceManager）相关联
   - 通用配置文件配置不需要设置configCategory、configGroup和configLevel字段

2. **分组逻辑**：
   - 如果参数值与某个特定角色相关，则需要设置configCategory="role"和对应的configGroup
   - 如果参数是通用配置，则不需要设置configCategory、configGroup和configLevel字段
   - 系统会根据参数名称自动识别其所属的配置文件

3. **自定义配置特殊处理**：
   - 自定义配置项必须设置 `configCategory = "file"`、`configGroup = "对应的配置文件名"` 和 `configLevel = "custom"`
   - 自定义配置通常放在独立的自定义分组中

### 6.3 配置分组在前端UI中的体现

配置分组机制直接影响前端UI的展示方式：

1. **一级分组**：分为角色配置和文件配置
   - 角色配置：通过configCategory="role"标识
   - 文件配置：通用配置文件参数，不需要设置configCategory
2. **二级分组**：
   - 角色配置：按照configGroup细分为具体角色
   - 文件配置：系统根据参数名称自动识别所属的配置文件
3. **三级分组**：
   - 角色配置：按照configLevel区分基础配置和高级配置
   - 自定义配置：通过configLevel="custom"标识

这种层次化的分组结构使得用户可以快速定位和修改特定类型的配置参数。

### 6.4 配置分组与Kubernetes部署的关系

在Kubernetes部署模式下，配置分组机制与以下特性紧密结合：

1. **configTargetRoles**：
   - 在configWriter中定义，指定哪些角色需要接收特定的Kubernetes配置
   - 例如：`"configTargetRoles": "ResourceManager,NodeManager,HistoryServer,TimelineServer"`

2. **bindRole**：
   - 将端口配置绑定到特定角色，确定哪个角色的Pod应该暴露哪些端口
   - 与configGroup协同工作，确保端口配置应用到正确的角色

3. **Kubernetes特定配置**：
   - 通常使用 `configCategory = "kubernetes"` 标识Kubernetes特定配置
   - 这些配置通过特殊的配置生成器（如kubernetes.config.persistent-volume-claims）处理

## 7. 端口与角色绑定机制详解

在Kubernetes部署模式下，服务的网络暴露通过两种方式配置：

### 7.1 通过parameters中的绑定参数配置

某些重要的端口配置直接在参数定义中指定，例如：

```json
{
  "name": "dfs.namenode.http-address.${dfs.nameservices}.nn1",
  "value": "${nn1}:9870",
  "bindRole": "NameNode",         // 将此端口绑定到NameNode角色
  "serviceType": "NodePort",      // 创建NodePort类型服务
  "portNumber": "9870",           // 容器内的端口号
  "nodePort": "30870"             // 节点上暴露的端口
}
```

这种方式的特点：
- 为具有固定通信端口的重要服务组件指定端口映射
- 端口配置与服务参数定义集成在一起
- 系统会自动为这些参数生成对应的Kubernetes Service资源

### 7.2 通过kubernetes.config.services配置

第二种方式是通过`kubernetes.config.services`配置文件和相关参数：

```json
{
  "name": "node_port_mappings",
  "type": "multipleWithKey",
  "value": [{"9870": "30870"}],
  "configCategory": "kubernetes",
  "configGroup": "kubernetes.config.services"
}
```

这种方式的特点：
- 更灵活，可以为任何端口配置映射
- 通过`configTargetRoles`字段确定配置应用的角色范围
- 适合配置辅助端口或非标准端口

### 7.3 bindRole的工作机制

`bindRole`参数在端口映射中起关键作用：

1. **服务选择器关联**：
   - 决定Kubernetes Service资源中的selector标签
   - 例如`bindRole: "NameNode"`会生成选择器`app: namenode`
   - 确保服务流量正确路由到对应角色的Pod

2. **服务资源生成**：
   - 系统会根据bindRole、serviceType、portNumber和nodePort生成相应的Service资源
   - 对于同一角色的多个端口，可能合并到同一个Service中或创建多个Service

3. **部署时处理**：
   - 当角色实例部署到Kubernetes中时，系统自动应用所有绑定到该角色的端口配置
   - 如未设置bindRole，则端口配置不会应用到任何角色

### 7.4 典型端口绑定示例

HDFS服务中常见的端口绑定配置：

| 参数名 | bindRole | serviceType | 端口 | 用途 |
|-------|----------|------------|------|------|
| dfs.namenode.rpc-address.*.nn1 | NameNode | ClusterIP | 8020 | NameNode RPC通信 |
| dfs.namenode.http-address.*.nn1 | NameNode | NodePort | 9870→30870 | NameNode Web UI |
| dfs.datanode.address | DataNode | ClusterIP | 1026 | DataNode数据传输 |
| dfs.namenode.shared.edits.dir | JournalNode | ClusterIP | 8485 | 编辑日志共享 |
