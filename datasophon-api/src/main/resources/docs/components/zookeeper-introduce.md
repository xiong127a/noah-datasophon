# Apache ZooKeeper 组件介绍

## ZooKeeper 是什么

Apache ZooKeeper 是一个开源的分布式协调服务。它为大型分布式计算系统提供了一套简单而强大的原语，用于解决分布式应用中常见的一些协调问题，如配置管理、命名服务、分布式同步、组成员管理等。

ZooKeeper 的设计目标是提供一个高性能、高可用、严格有序的协调服务。它通过一个类似于文件系统的树形命名空间来组织数据，每个节点称为 ZNode。客户端可以创建、读取、更新和删除 ZNode，并可以在 ZNode 上设置监视 (Watch)，以便在 ZNode 发生变化时获得通知。

## 核心概念

理解 ZooKeeper 的核心概念对于有效使用它至关重要：

### ZNode (ZooKeeper Data Node)
ZNode 是 ZooKeeper 树形命名空间中的数据节点。每个 ZNode 都可以存储少量数据 (通常不超过1MB) 和元数据 (如版本号、时间戳、ACL等)。ZNode 的路径是唯一的，类似于文件系统路径 (例如 `/app1/config/db_host`)。

ZNode 可以分为几种类型：
*   **持久节点 (Persistent Nodes)**: 一旦创建，除非被显式删除，否则会一直存在，即使创建该节点的客户端会话结束。
*   **临时节点 (Ephemeral Nodes)**: 生命周期与创建该节点的客户端会话绑定。当客户端会话因断开连接或超时而结束时，该会话创建的所有临时节点都会被自动删除。临时节点不能有子节点。
*   **顺序节点 (Sequential Nodes)**: 创建时，ZooKeeper 会自动在节点路径后附加一个单调递增的数字。例如，如果客户端请求创建 `/app1/task-`，ZooKeeper 可能会创建一个名为 `/app1/task-0000000001` 的节点。持久节点和临时节点都可以是顺序节点。
*   **容器节点 (Container Nodes)**: (自 ZooKeeper 3.5.3 版本引入) 当容器节点的最后一个子节点被删除后，容器节点本身会在一段时间后被 ZooKeeper 服务器自动删除。用于管理子节点，本身不存储重要数据。
*   **TTL 节点 (TTL Nodes)**: (自 ZooKeeper 3.5.3 版本引入，默认禁用) 临时节点和持久节点都可以配置 TTL (Time To Live)。如果节点在 TTL 时间内没有被修改且没有子节点，它将被自动删除。

### Watch (监视)
Watch 是 ZooKeeper 的一个核心机制，允许客户端在某个 ZNode 上注册一个一次性的触发器。当该 ZNode 的状态 (数据内容、子节点列表) 发生变化时，设置了 Watch 的客户端会得到通知。一旦 Watch 被触发，它就会被移除，如果客户端希望继续监视该节点，需要重新注册 Watch。

Watch 主要用于：
*   **数据变更通知**: 监视 ZNode 数据的变化。
*   **子节点变更通知**: 监视 ZNode 子节点列表的变化 (增、删)。
*   **ZNode 创建/删除通知**: 监视 ZNode 是否被创建或删除。

### 会话 (Session)
客户端通过 TCP 连接到 ZooKeeper 服务集群中的某一个服务器来建立会话。会话具有超时机制。如果客户端在会话超时时间内未能与服务器成功通信 (例如通过心跳)，则会话被认为已过期，该会话创建的临时节点将被删除。

### ACL (Access Control Lists)
ZooKeeper 为每个 ZNode 提供了访问控制列表 (ACL) 机制，用于控制哪些客户端以及它们可以对该 ZNode 执行哪些操作 (如读取、写入、删除、创建子节点、管理ACL等)。ACL 基于认证方案 (如 Digest, SASL, IP) 来识别客户端。

### 集群模式 (Ensemble)
为了实现高可用性和高性能，ZooKeeper 通常以集群模式 (称为 ZooKeeper Ensemble) 运行。一个 Ensemble 通常由奇数个服务器组成 (例如3、5、7个)。
*   **Leader**: 集群中有一个服务器被选举为 Leader。Leader 负责处理所有写请求 (创建、更新、删除 ZNode)。
*   **Follower**: 集群中的其他服务器称为 Follower。Follower 接收并处理客户端的读请求，并将写请求转发给 Leader。Follower 也参与 Leader 选举过程。
*   **Observer**: (可选) Observer 类似于 Follower，它们也接收客户端连接并处理读请求、转发写请求，但不参与投票和选举过程。引入 Observer 可以提高集群的读性能和可伸缩性，而不会增加选举的复杂性和开销。

### Quorum (法定人数)
ZooKeeper 集群中的写操作和 Leader 选举都需要得到超过半数 (Quorum) 的服务器的确认。例如，在一个包含5个服务器的集群中，至少需要3个服务器同意，一个写操作才能成功提交，或者一个新的 Leader 才能被选举出来。这就是为什么 ZooKeeper 集群通常配置奇数个服务器的原因。
这种基于 Quorum 的机制保证了数据的一致性和集群的容错性。一个包含 `2n+1` 个服务器的集群可以容忍 `n` 个服务器的故障。

### Zab (ZooKeeper Atomic Broadcast)
Zab 是 ZooKeeper 用于在集群中所有服务器之间保持状态同步和确保操作有序性的原子广播协议。它负责处理 Leader 选举、数据复制和故障恢复。
Zab 保证了以下特性：
*   **全局有序**: 所有写操作按照 Leader 广播的顺序被应用。
*   **可靠传递**: 如果一个消息被一个服务器处理，那么它最终会被所有非故障服务器处理。
*   **事务性**: 更新要么全部成功，要么全部失败。

## 核心架构

一个典型的 ZooKeeper 服务架构包括：
1.  **ZooKeeper 服务器集群 (Ensemble)**: 由多个 ZooKeeper 服务器组成，共同提供协调服务。
2.  **客户端库 (Client Library)**: 应用程序通过 ZooKeeper 客户端库与 ZooKeeper 集群交互。客户端库负责维护与服务器的连接、发送请求、接收响应和处理 Watch 事件。

**工作流程简述**:
*   客户端连接到 Ensemble 中的任意一个服务器。
*   如果是读请求，该服务器可以直接响应 (如果其数据是最新的)。
*   如果是写请求，该服务器会将请求转发给 Leader。
*   Leader 处理写请求，并通过 Zab 协议将状态变更广播给所有 Follower。
*   一旦超过半数的服务器确认了该变更，Leader 就会提交该变更，并通知客户端操作成功。

## 关键特性

### 简单性 (Simplicity)
ZooKeeper 提供了一个非常简单的类似文件系统的 API，易于理解和使用。

### 可靠性 (Reliability)
通过集群模式和 Zab 协议，ZooKeeper 保证了数据的一致性和高可用性。只要集群中超过半数的服务器正常工作，服务就是可用的。

### 有序性 (Ordering)
ZooKeeper 会为每个更新操作分配一个全局唯一的、单调递增的事务 ID (zxid)。这保证了所有操作的严格顺序性，对于实现分布式锁和队列等复杂协调逻辑至关重要。

### 高性能 (Performance)
ZooKeeper 在读多写少的场景下表现优异。读请求可以在任何连接的服务器上处理，而写请求虽然需要经过 Leader 和 Quorum 确认，但也经过了高度优化。

### 可扩展性 (Scalability)
可以通过增加 Observer 节点来扩展 ZooKeeper 集群的读吞吐能力。

## 常见用例

ZooKeeper 作为分布式协调的基石，被广泛应用于各种分布式系统中：

*   **配置管理**: 分布式应用可以将它们的配置信息存储在 ZooKeeper 的 ZNode 中。当配置发生变化时，应用可以通过 Watch 机制得到通知并动态更新配置。
*   **命名服务**: 提供一个全局唯一的名称与服务地址或资源的映射。例如，微服务架构中的服务发现。
*   **分布式锁**: 利用 ZooKeeper 的临时顺序节点和 Watch 机制，可以实现公平或非公平的分布式锁，用于控制对共享资源的互斥访问。
*   **分布式队列**: 利用顺序节点可以实现先进先出 (FIFO) 的分布式队列。
*   **组成员管理/集群管理**: 监控集群中节点的存活状态。每个节点启动时创建一个临时节点，如果节点宕机，临时节点会自动删除，其他节点通过 Watch 感知到变化。
*   **Leader 选举**: 多个节点竞争创建一个特定的临时节点，成功创建的成为 Leader。如果 Leader 宕机，其他节点会再次竞争。
*   **分布式屏障 (Barrier)**: 确保一组分布式进程在达到某个同步点之前都必须等待。
*   **发布/订阅**: 一方发布信息到某个 ZNode，多方订阅该 ZNode 以接收信息。

许多著名的分布式系统，如 Apache Hadoop (YARN, HDFS NameNode HA), Apache HBase, Apache Kafka, Apache Solr, Apache Storm 等，都依赖 ZooKeeper 进行核心的协调工作。
